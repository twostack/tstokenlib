Reading this

A script is named for the output it locks

PP3 is the locking script on round N's output 3. It executes when round N+1 spends it at input 3. Those are two different positions with two different numbers, and the page keeps them apart everywhere: a box's outputs are what it creates, and an arrow arriving at a box is what consumes them.

Three relationships appear in the map, and telling them apart is the whole design. A solid arrow is a spend. A dotted line is a claim made about a transaction that has not been spent yet: PP3 pins an outpoint the next round must spend, and PP1 certifies what the script at that outpoint actually is.

The chain

Rounds and witnesses alternate; slot transactions drop in from above

Script families

Five kinds of script, colour-coded throughout

PP1_SP

Locks round out1. Runs when the witness spends it. Rebuilds its own round byte for byte and certifies the next verifier slot. 10,294 B

PP2

Locks round out2. Runs in the witness. Forces every witness input to come from this round and the witness output to pay the owner. 1,366 B

PP3

Locks round out3 and holds the pool balance. Runs when the next round spends it, at input 3. Pins the verifier slot that round must also spend, and requires that round's output 3 to run this same program: a forward covenant, so the balance can never move into a weaker script. No owner and no burn path. 49,182 B

V

Locks slot transaction out0, one satoshi. Runs as input 2 of the round it verifies. Today a stub: a header push then OP_DROP OP_1. 240 B

P2PKH and metadata

Change out0, the metadata OP_FALSE OP_RETURN at out4, and the witness's single ModP2PKH output. No covenant on any of them.

The arrangement

Three scripts, none of them sufficient alone

PP1 is the locking script on round N+1's output 1. It does not execute when that round is mined; it executes later, when witness N+1 spends it. By then the round is confirmed and its withdrawal outputs are already spendable, so PP1 can never gate its own round's money. That is why its checks point one round ahead.

ScriptLocksExecutes whenDoes what
V_N Y_N out0 round N+1 spends it at in2 Verifies the proof, rebuilds the round's outputs against hashOutputs, checks the withdrawal list and the balance equation. This is the gate on money, and it sits in the same transaction as the payout.
PP3_N round N out3 round N+1 spends it at in3 Requires the round's input 2 to be the outpoint it named, so V cannot simply be left out, and the round's output 3 to run PP3's own program, so the balance cannot move into a weaker script. Knows the address, not the tenant.
PP1_N round N out1 witness N spends it at in1 Certified, one round earlier, that the outpoint PP3_N names holds this pool's verifier carrying header N. Can inspect, but arrives too late for its own round.

PP3 supplies the timing and PP1 supplies the sight. The ordering is safe because round N+2 spends witness N+1's output 0, so witness N+1 always exists first and the certificate is in place before the pin it describes is ever tested.

Modes

Who produces the proof decides what Y looks like

The pool has two operating modes. They differ in one question: does the coordinator run a prover? Everything else in the map above is unchanged, including PP1, PP2, PP3 and the round-witness alternation. What changes is how many verifier outputs a slot transaction carries, and therefore what a round costs per transfer.

Direct-slot

The coordinator proves nothing

Each user proves their own spend. Y_N carries K spend-verifier outputs plus one subtree-append slot, and the round spends all of them. The coordinator only assembles transactions.

an MVP, and any deployment where the coordinator's prover is not yet built or not yet trusted to exist

Aggregated

The coordinator folds K proofs into one

A recursive prover reduces every spend in the round to a single proof. Y_N carries one output, the aggregated root verifier. This is the mode the design document describes and the one the map above draws.

1
Cost
~356 s for a 256-transfer round on one machine
Needs
the recursion stack, a GPU-capable prover, and machine time
Good for
throughput; per-transfer cost is the only way the pool scales

Neither mode makes the coordinator trusted. In both, a round is only mineable if the verifier accepted it, and the coordinator's failure mode is that the pool stops, not that funds move. They are kept as separate solutions selected by coordinator configuration rather than a migration path, because the aggregated prover is a large piece of machinery and direct-slot has to keep working without it.

Open conflict. The certificate PP1 writes requires Y to have exactly one input and one output, which is what forces V to be output 0. Direct-slot's K + 1 outputs cannot satisfy that check as written, so the two are currently incompatible. Options, none chosen: give each verifier its own single-output Y, so a round spends K + 1 slot transactions; relax the check to "output 0 is V" with a proven output count; or give direct mode its own PP1 variant. The first keeps the covenant untouched and costs transaction overhead; the second weakens a property that has a test defending it.

Status

What the map draws that does not exist yet

  • V is a stub. Today it is a header push followed by OP_DROP OP_1, 240 bytes. The real one is roughly 1.5 MB and carries the hashOutputs rebuild, the proof check and the balance equation. Everything around it is real, which is what makes the covenant testable without it.
  • Withdrawals are ungated, not impossible. As of 2026-09-21 PP1 emits a variable output tail: receipts then withdrawals, each rebuilt from a fixed template with only its hash, commitment and amount free, with the count divided out of the blob sizes rather than pushed. That is 6,981 of the 10,294 bytes on this page's PP1 boxes. What is still missing is the gate, which is V's balance equation, not the tail.
  • Deposits are unbuilt. The covenant outputs, their SIGHASH_SINGLE receipt binding and the refund timelock are designed and not written.
  • Everything else verifies. Genesis, two full rounds, both witnesses and every PP3 spend are accepted by the interpreter, and the sizes on this page come from that run rather than from the design document.
